# 처음부터 다시 만든다면 무엇을 남길까

목표는 지금과 같다고 가정합니다. 업무와 생활에 쓰는 작은 도구 여러 개를 Claude와 함께 만들어 굴리는 것입니다. 판단 기준은 두 가지입니다. 실제로 쓰이고 있는가(실행 기록), 그리고 다시 만들 때 같은 실수를 반복하게 만드는 구조인가.

## 남길 것

**1. 뉴스카드 작성 규칙(`docs/newscard-template.md`)과 매일 아침 루틴.** 이 저장소에서 꾸준히 실제로 돌아가는 것은 이 둘뿐입니다(8월 1일부터 108일 중 91일치 news-*.md가 쌓였고, 빠진 17일은 대부분 8~9월). 코드가 아니라 "무엇을 어떤 기준으로 쓰는가"를 적은 규칙이 자산입니다. 다시 만들어도 그대로 가져갑니다.

**2. 모션 분석의 단계별 스크립트 구조.** 사전 점검 → 요소 분할 → 사진 → 리스크 → 문서가 각각 독립된 CLI이고, 사이를 파일로 주고받습니다. 이 구조 덕분에 오늘 가짜 단계 스크립트로 파이프라인 전체를 2초 만에 테스트할 수 있었습니다. 분석 알고리즘(손·자세 추적, 서블릭, 사이클 정합)은 도메인 지식이 들어간 부분이라 그대로 둡니다. 오늘 넣은 단계 기록(`_stages.json`)은 처음부터 있어야 했던 부분입니다.

**3. 허브의 규칙들.** 항목 상태(new/ready/tombstone), 동기화가 바꿔도 되는 필드 표(`UPDATE_RULES`), 불변식 검사(`--check`). 데이터를 어디에 두든 이 규칙은 같습니다.

**4. 한 파일짜리 웹앱 방식.** 무음카메라, 홈 화면 정리기, 검수·존 도구는 HTML 하나로 끝납니다. 빌드도 의존성도 없어서 고치기 쉽고, 실제로 오늘 고친 버그 중 이 방식 때문에 생긴 것은 없습니다.

## 버릴 것 또는 바꿀 것

**1. 앱마다 브랜치 하나, main은 거의 비어 있는 구조.** 가장 큰 문제입니다.
- 예약 실행과 main push 트리거는 기본 브랜치에 있는 워크플로만 돕니다. 그래서 카카오 뉴스(`daily-news.yml`)와 무음카메라 배포(`deploy.yml`)는 **한 번도 실행되지 않았습니다**. 만들어 놓고 돈 적이 없는 앱 두 개가 이 구조에서 나왔습니다.
- 여러 앱을 한 번에 고칠 수 없습니다. 오늘도 앱마다 따로 작업 트리를 만들어 패치로 나눠야 했습니다.
- 다시 만든다면 main 하나에 앱마다 폴더(`apps/hub`, `apps/motion` …)를 두고, 브랜치는 작업 단위로만 짧게 씁니다. 워크플로는 `paths:` 필터로 앱별로 나눕니다.

**2. 허브 데이터를 HTML 안에 넣는 방식.** 오늘 허브에서 고친 복잡함의 대부분은 레지스트리가 페이지 안에 들어 있어서 생겼습니다. 저장할 때마다 페이지 전체를 다시 발행하니 동시 저장이 충돌하고, 충돌 뒤 초안을 다시 얹는 로직이 필요했습니다. 주간 동기화는 발행본을 내려받아 HTML을 수술한 뒤 다시 발행합니다. 코드와 데이터의 출처를 나누는 규칙도 따로 필요했습니다.
- 지금은 아티팩트에 공유 데이터베이스(`db` 기능)가 있습니다. 항목 하나가 문서 하나가 되면 저장 충돌은 그 항목에서만 일어나고, 에이전트는 HTML을 건드리지 않고 행만 추가합니다. `sync.py`의 HTML 처리, 초안 재적용, 코드/데이터 분리가 통째로 필요 없어집니다.
- 오늘 이걸 하지 않은 이유: 기존 기능을 깨지 않는다는 조건, 그리고 팀원이 쓰는 라이브 페이지의 저장 방식을 바꾸는 건 되돌리기 어려운 결정이기 때문입니다. 다음 큰 변경 때 1순위입니다.

**3. 뉴스 파이프라인 세 개.** 7월의 Python 카카오 발송기, 매일 루틴이 쓰는 마크다운 뉴스카드, Gemini로 그리는 만화 카드가 따로 있습니다. 실제로 돌아가는 건 마크다운 루틴뿐입니다. 만화 카드는 68번 모두 무료 한도로 실패했고, 카카오 발송기는 실행된 적이 없습니다. 다시 만든다면 루틴 하나에서 시작하고, 이미지 카드는 유료 등급을 쓸지 먼저 정한 뒤 붙입니다.

**4. 브라우저 도구 결과를 다운로드 폴더에서 찾아오는 방식(모션 `start.py`).** 사용자가 저장한 파일을 다운로드 폴더에서 "가장 최근 것"으로 추측합니다. 오늘 시간 조건을 붙여 다른 영상 파일을 집어 오는 버그는 막았지만, 근본적으로는 추측입니다. 다시 만든다면 `start.py`가 작은 로컬 서버를 띄우고, 도구가 결과를 그 서버로 바로 보내게 합니다.

## 한 줄로

남길 것은 규칙과 도메인 로직이고, 버릴 것은 "브랜치에 흩어진 앱"과 "페이지 안에 든 공유 데이터"입니다. 오늘 고친 버그의 상당수가 이 두 구조에서 나왔습니다.
