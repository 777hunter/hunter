# 동영상 모션 인식 / 동작 분석

작업 영상을 넣으면 동작을 인식해 작업요소로 나누고, 서블릭으로 분석하고,
사진을 뽑아 TWI 3열 작업지도서 초안까지 만든다.

## 가장 쉬운 방법 — 물어보는 대로만 하면 된다

명령어를 외울 필요 없다. 실행기를 더블클릭하면 나머지는 물어본다.

| 컴퓨터 | 할 일 |
| --- | --- |
| 윈도우 | `motion\실행.bat` 더블클릭. 영상 파일을 이 위로 끌어다 놓아도 된다 |
| 맥 | `motion/실행.command` 더블클릭. 처음 한 번은 오른쪽 클릭 > 열기 |
| 리눅스 | `bash motion/실행.sh` |

파이썬만 깔려 있으면 된다(없으면 안내가 뜬다). 나머지 도구는 처음 실행할 때
알아서 설치한다. 몇 분 걸리고, 그다음부터는 바로 뜬다.

실행기가 하는 일은 이렇다.

1. 컴퓨터에 있는 영상을 찾아서 목록으로 보여준다. 번호만 고르면 된다
2. 쓸 수 있는 영상인지 먼저 확인하고, 못 쓸 영상이면 이유를 말하고 멈춘다
3. 동작을 작업요소로 나눈 뒤, **브라우저를 자동으로 열어** 화면의 어디가
   부품박스고 어디가 지그인지 사각형으로 표시하게 한다
4. 이름·사진·문서 초안을 만든다
5. **다시 브라우저를 열어** 검수하게 한다. 저장하면 최종 문서가 나온다
6. 결과 폴더를 열어 준다

브라우저에서 저장한 `zones.json`, `review.json` 은 다운로드 폴더에 떨어지는데,
실행기가 알아서 찾아온다. 중간에 끊어도 다시 실행하면 이어서 한다.

결과는 영상이 있던 자리에 `작업표준_영상이름` 폴더로 생긴다.

> Node.js 가 없으면 워드 파일 대신 **인쇄용 HTML** 로 만든다. 브라우저에서 열어
> 인쇄 > PDF 로 저장하거나 워드에 붙여넣으면 된다. 내용은 같다.

## 직접 명령어로 (자동화하거나 옵션을 조절할 때)

### 설치

```bash
python3 -m venv .venv && source .venv/bin/activate     # 윈도우: .venv\Scripts\activate
pip install -r motion/requirements.txt
cd motion && npm install && cd ..                      # 워드 문서 렌더러
```

리눅스 헤드리스 서버라면 `sudo apt-get install -y libegl1 libgl1 libgles2` 가 더 필요하다.
모델 파일은 첫 실행 때 `~/.cache/mediapipe` 로 자동 내려받는다.

한글 캡션에 쓸 글꼴이 있어야 한다. 윈도우·맥은 기본 글꼴로 잡히고, 리눅스는
`sudo apt-get install fonts-nanum` 또는 `--font /경로/글꼴.ttf`.

### 세 번 돌리면 끝난다

```bash
# 1차 — 존 없이. 쓸 수 있는 영상인지 보고, 손이 어디를 집고 놓는지 찍어낸다
python motion/run_all.py work.mp4 --out-dir out

# zone_tool.html 을 브라우저에서 열고 영상 + out/work_elements.csv 를 얹어
# 부품박스·지그·배출구를 사각형으로 표시하고 zones.json 저장

# 2차 — 이름이 붙고 사진이 나오고 문서 초안이 나온다
python motion/run_all.py work.mp4 --out-dir out --zones zones.json \
    --job-name "브래킷 조립" --process "1공정" --author "홍길동"

# review_tool.html 을 열고 out 폴더 + 영상을 넣어 검수 (여기가 30분)
# 급소의 이유를 채우고 사진을 고른 뒤 review.json 저장

# 3차 — 최종 문서
python motion/run_all.py work.mp4 --out-dir out --zones zones.json \
    --review review.json --force
```

이미 만들어진 산출물은 건너뛴다. 다시 만들려면 `--force`, 특정 단계만 돌리려면
`--from shots --to ji`.

불량 이력이 있으면 `--defects defects.csv`(열: `불량모드`, `건수`, `키워드`)를
붙인다. 포카요케 신호에 실제 불량 모드가 연결되고 심각도가 올라간다.

### 영상 촬영 조건

| 항목 | 기준 |
| --- | --- |
| 각도 | 손이 계속 보이는 45도 오버숄더 또는 탑다운 |
| 프레임 | 60fps 권장 (30fps 는 쥐기 전이가 2~3프레임이라 놓치기 쉽다) |
| 길이 | 최소 5사이클, 권장 10사이클 |
| 손 크기 | 손목–중지뿌리 길이가 40px 이상 |
| 조명 | 역광·저조도 피하기. 장갑은 무늬 없는 단색이 낫다 |

### 먼저 사전 점검부터

```bash
python motion/preflight.py work.mp4 --out-dir out
```

10분 영상을 다 돌린 뒤에 "손이 안 잡혔다"를 알면 늦다. 영상 곳곳에서 연속
프레임 덩어리를 표본으로 떠서 몇 초 만에 판정한다.

- **검출률·손 크기·프레임레이트**로 진행 가능 / 조건부 / 재촬영 권장을 낸다
- **쥠 정도 분포**에서 쥔 상태와 편 상태를 가르는 지점을 오츠 방식으로 찾아
  `--close-curl`, `--open-curl` 을 추천한다. 이게 이 시스템에서 제일 자주
  어긋나는 값이다. 부품이나 공구를 쥐면 손가락이 완전히 안 접혀서 기본값으로는
  쥐기가 안 잡히고, 그러면 요소 분할부터 무너진다
- **손목 속도 분포**에서 `--still-speed`, `--move-speed` 를 추천한다.
  속도는 같은 표본 덩어리 안의 연속 프레임끼리만 재기 때문에 본 파이프라인과
  같은 눈금이다

`run_all.py` 는 이 추천값을 자동으로 적용한다(`--no-auto-tune` 으로 끌 수 있다).
분리도가 0.35 아래로 나오면 두 무리로 안 갈린다는 뜻이니 추천값을 그대로 믿지
말고 `*_preflight.png` 의 분포를 직접 봐야 한다.

### 처리 시간

측정 기준 CPU에서 초당 약 40프레임을 처리한다. 30fps 영상이면 대략 영상 길이의
0.8배, 10분 영상이면 7~8분쯤 걸린다(요소 분할 단계 기준, 나머지 단계는 몇 초).
`--stride 2` 로 절반만 볼 수 있지만 권하지 않는다. 30fps에서 쥐기 전이가 2~3프레임인데
건너뛰면 그 전이를 놓쳐 요소 경계가 뭉개진다.

```
out/

  work_elements.csv              요소 전체 (존 그릴 때 이 파일을 얹는다)
  work_standard.csv / .json      표준 요소표, 정미시간, 표준시간
  work_cycles.svg                사이클 정합 차트
  work_shots.json, shots/        요소별 후보 사진 3장과 주석본
  work_shots.png                 대표 사진 시트 (검수용)
  work_risks.csv / .json         포카요케 리스크 신호
  work_작업지도서.docx            TWI 3열 작업지도서 + 부록 A/B/C
```

### 막히면 보는 순서

1. `*_preflight.png` — 손이 안 잡히면 여기서 끝이다. 재촬영
2. `python motion/therblig_tag.py work.mp4 --annotate` — 쥐기(G)·놓기(RL)가
   제대로 잡히는지 오버레이 영상으로 확인. 안 잡히면 `--close-curl` 을 올린다
3. `작업요소가 2개밖에 안 나온다` — RL 이 안 잡히는 것이다. 2번으로
4. `주기 신뢰도가 낮다` — 사이클당 요소 수를 알면 `--period N` 으로 직접 준다
5. `명명률이 낮다` — zone_tool 에 elements.csv 를 얹어 점이 찍혔는데 존이 없는
   자리를 찾는다

동영상 파일을 넣으면 프레임마다 사람 관절 33개를 뽑아 관절 각도, 반복 횟수,
움직임 구간을 계산하고 스켈레톤을 덧씌운 영상까지 내보내는 CLI.

## 뭘 쓸지 먼저

동작 분석은 접근이 세 갈래고, 목적에 따라 답이 다르다.

1. **키포인트(포즈 추정) + 규칙** — 지금 이 폴더가 하는 방식.
   MediaPipe Pose로 관절 좌표를 뽑고 각도·속도로 규칙을 세운다.
   CPU만으로 실시간에 가깝고, "왜 그렇게 판정했는지"가 각도로 설명된다.
   스쿼트 개수, 무릎 각도 부족, 좌우 비대칭 같은 정량 피드백에 맞다.
   한계: 동작 이름을 스스로 배우지 못하고, 사람마다 임계값을 손봐야 한다.

2. **영상 분류 모델** — VideoMAE, X3D, SlowFast 같은 3D CNN/트랜스포머에
   클립을 통째로 넣어 "스쿼트/데드리프트/걷기"를 분류한다. 라벨링된 학습
   데이터와 GPU가 필요하지만, 규칙으로 못 쓰는 미묘한 동작을 잡는다.
   HuggingFace `videomae-base-finetuned-kinetics`로 바로 시험해볼 수 있다.

3. **키포인트 시퀀스 분류** — 1번으로 뽑은 좌표 시퀀스를 LSTM/GCN
   (ST-GCN, PoseC3D)에 넣는다. 배경·의상에 안 흔들리고 학습 데이터가 훨씬
   적게 든다. 커스텀 동작 몇 개를 인식시켜야 할 때 가성비가 제일 좋다.

**추천 순서**: 1번으로 시작해서 각도 규칙으로 안 되는 게 뭔지 확인한 뒤,
그때 3번으로 넘어간다. 2번은 라벨 데이터가 이미 있을 때만.

여러 명이 동시에 나오거나 정확도가 더 필요하면 포즈 추정기를 YOLO11-pose
또는 RTMPose로 바꾸면 된다. 아래 코드는 `pose_core.py`의 추출부만 갈아끼우면
나머지 분석 로직을 그대로 쓸 수 있게 나눠 놨다.

## 사용

```bash
python motion/analyze.py squat.mp4 --out-dir out --exercise squat --annotate
```

주요 옵션

| 옵션 | 설명 |
| --- | --- |
| `--exercise` | `auto`(전부 시도) 또는 `squat pushup curl situp jumping_jack` 중 복수 지정 |
| `--model-variant` | `lite`(빠름) / `full`(기본) / `heavy`(정확) |
| `--stride N` | N프레임마다 1장만 처리. 긴 영상 훑을 때 |
| `--annotate` | 스켈레톤·각도·카운트 오버레이 mp4 저장 |
| `--dump-landmarks` | CSV에 33개 키포인트 원본 좌표까지 포함 |

## 출력

- `*_frames.csv` — 프레임별 8개 관절 각도, 상체 기울기, 정규화된 움직임 속도
- `*_summary.json` — 반복 횟수와 각 반복의 시각, 관절 각도 min/max/mean,
  좌우 비대칭, 움직임이 있었던 구간(초 단위), 검출률
- `*_annotated.mp4` — 눈으로 검증할 오버레이 영상

`detection_rate`가 0.9 아래면 결과를 믿지 마라. 대개 사람이 프레임 밖으로
나가거나, 옆모습이라 반대쪽 관절이 가려졌거나, 조명이 문제다.

## 반복 카운트가 동작하는 방식

관절 각도 신호에 결측 보간 + 이동평균을 걸고, 히스테리시스 2단
임계값(`low`/`high`)으로 상태 기계를 돌린다. `high → low → high`가 1회.
한 임계값만 쓰면 노이즈로 중복 카운트가 나기 때문에 두 개를 쓴다.
임계값은 `metrics.py`의 `EXERCISES`에 모아 뒀고, 촬영 각도나 대상자에 따라
여기만 고치면 된다. 새 동작을 추가할 때도 신호 함수 하나 + 임계값 두 개면 끝.

## 알려진 한계

- 한 명만 추적한다(`num_poses=1`). 여러 명이면 위 2번 항목대로 교체.
- 카메라가 정면/측면 어느 쪽이냐에 따라 각도가 달라진다. 스쿼트 무릎 각도는
  측면, 좌우 비대칭은 정면이 정확하다.
- 3D 월드 좌표는 골반 기준 상대 좌표라 절대 위치·실제 이동거리는 못 준다.
- 손가락·표정은 별도 모델(HandLandmarker, FaceLandmarker)이 필요하다.

## 서블릭(Therblig) 자동 태깅

작업 영상에서 손 21개 랜드마크를 뽑아 길브레스의 서블릭 기호를 자동으로
붙이고, 양수동작분석표(SIMO chart)를 그린다.

```bash
python motion/therblig_tag.py work.mp4 --out-dir out --annotate
```

### 판정 규칙

신호는 두 개다. **쥠 정도(curl)** 는 손가락 끝 4개에서 손바닥 중심까지의 평균
거리를 손 길이로 나눈 값이고, **속도** 는 손목 이동거리를 손 길이로 나눠
초당으로 환산한 값이다. 둘 다 손 크기로 정규화해서 카메라 거리에 무관하다.

| 상태 | 서블릭 | 분류 |
| --- | --- | --- |
| 쥠 상태로 전이 중 | G 쥐기 | 제1류 |
| 폄 상태로 전이 중 | RL 내려놓기 | 제1류 |
| 쥠 + 빠른 이동 | TL 운반 | 제1류 |
| 쥠 + 왕복 운동 | U 사용 | 제1류 |
| 쥠 + 느린 이동 | P 바로놓기 | 제2류 |
| 쥠 + 정지 | H 잡고있기 | 제3류 |
| 폄 + 이동 | TE 빈손이동 | 제1류 |
| 폄 + 정지 | D 지연 | 제3류 |

G와 RL은 속도가 아니라 쥠 상태가 실제로 **바뀌는 지점**에서만 나온다.
히스테리시스로 쥠/폄 상태를 먼저 확정하고, 상태가 뒤집히는 프레임 주변에서
손가락이 실제로 움직이는 구간까지만 확장해 태깅한다. 이렇게 안 하면 손 떨림이나
검출 흔들림 때문에 G/RL이 남발된다.

U(사용)는 왕복 운동으로 잡는다. 0.5초 창 안의 이동 경로 길이를 순변위로 나눠서
비율이 크면(닦기, 조이기처럼 제자리 왕복) 사용으로 본다.

### 자동으로 못 내는 것

18종 중 8종만 낸다. 찾기(Sh), 발견(F), 선택(St), 조립(A), 분해(DA), 검사(I),
미리놓기(PP), 계획(Pn), 휴식(R)은 손 운동학만으로 구분이 안 된다. 조립과 분해는
대상물이 합쳐지는지 갈라지는지를 봐야 하고, 검사와 계획은 시선과 의도의 문제다.
찾기·선택은 눈이 움직이는 동안 손이 멈춰 있어서 지연(D)과 파형이 같다.

이 아홉 개까지 필요하면 방법은 둘이다. 대상물 검출(YOLO 등)을 붙여 손과 부품의
접촉·분리를 보거나, 태깅된 구간을 사람이 한 번 훑으면서 D로 뭉뚱그려진 것을
Sh/St로 쪼개는 것이다. 후자가 현실적이다. 자동 태깅의 값어치는 100% 정확도가
아니라, 10분짜리 영상에서 사람이 볼 구간을 30초로 줄여주는 데 있다.

### 출력

- `*_therblig_segments.csv` — 손별 서블릭 구간(시작·끝·지속시간·분류)
- `*_therblig_frames.csv` — 프레임별 curl, 속도, 왕복비율, 태그
- `*_therblig_summary.json` — 서블릭별 시간·횟수, 분류별 구성비,
  유효/무효 비율, 사이클(주기·쥠시간), 양손 유휴 시간
- `*_simo.svg` — 양수동작분석표. 좌수/우수 두 줄, 시간축, 분류별 구성비 막대
- `*_therblig.mp4` — 손 스켈레톤을 서블릭 색으로 칠한 검증용 영상

### 임계값 튜닝

기본값은 실측 기준이다. 주먹 쥔 손의 curl이 0.28, 편 손이 1.5로 나와서
`--close-curl 0.65`, `--open-curl 1.05`를 기본으로 잡았다. 공구나 부품을 쥐면
손가락이 완전히 안 접혀 curl이 0.8~1.0까지 올라가므로, 대상물이 크면
`--close-curl`을 올려야 한다. `*_therblig_frames.csv`의 curl 열을 그려서
쥔 구간과 편 구간의 실제 분포를 보고 두 봉우리 사이에 두 임계값을 놓으면 된다.
속도는 `--still-speed`, `--move-speed`로 같은 방식으로 맞춘다.

### 촬영 가이드

손이 프레임 안에 계속 있어야 한다. 작업대 위 45도 오버숄더나 탑다운이 제일
안정적이다. 손이 몸에 가려지거나 프레임을 벗어나면 그 구간은 `-`(미검출)로
빠지고, 요약의 유효/무효 비율은 미검출을 뺀 시간 기준으로 계산된다.
빠른 손 동작은 30fps에서 쥐기 전이가 2~3프레임에 끝나 놓치기 쉬우므로 60fps를
권한다. 거울 촬영이라 좌우가 뒤집혔으면 `--swap-hands`.

MediaPipe의 좌우 판정은 프레임마다 뒤집히는 일이 잦아서, 이전 프레임 손목
위치에 가장 가까운 쪽으로 추적해 슬롯을 고정한다. 요약의
`handedness_conflicts`가 프레임 수 대비 크면 좌우 배정을 의심해야 한다.

### 검증 상태

합성 신호(4사이클 픽앤플레이스)로 상태 기계를 시험했을 때
`TE → G → TL → P → RL → D` 순서를 정확히 재현했고, 실제 손 이미지로 만든
합성 영상에서는 주기 2.5초를 표준편차 0.00으로, 사이클 4회를 정확히 잡았다.
다만 이건 깨끗한 합성 데이터고, 실제 작업 영상에서는 임계값 조정이 필요하다.

## M1 — 작업요소 분할과 표준 순서 도출

작업표준서 자동화의 첫 단계. 서블릭을 작업요소로 묶고, 반복 사이클을 찾아 정렬해서
표준 순서와 요소별 시간을 뽑는다.

```bash
python motion/build_standard.py work.mp4 --out-dir out --allowance 0.15
```

### 서블릭을 작업요소로 묶는 규칙

서블릭은 0.2~2초라 30초 작업에 40개가 나온다. 작업표준서에 쓸 수 있는 단위는
3~6초짜리 작업요소다. 묶는 기준은 서블릭 안에 이미 들어 있다.

**요소 구분점은 우세손의 `RL`(내려놓기) 또는 `U`(사용)가 끝나는 지점이다.**
손에서 물건이 떠나거나 공구 사용이 끝나는 순간이 작업이 한 덩어리 끝나는
지점이기 때문이다. 구분점 사이의 시간은 빈틈 없이 어느 요소엔가 속한다.
앞쪽의 빈손이동과 대기는 뒤따르는 작업을 위한 준비이므로 뒤 요소에 포함된다.

우세손은 `G`(쥐기) 횟수가 많은 쪽으로 자동 판정하고, `--dominant`로 강제할 수 있다.
보조손 동작은 같은 요소에 병합되어 `support` 열에 기록된다.

### 사이클을 찾고 맞추는 방법

요소마다 특징 벡터를 만든다. **집는 위치와 놓는 위치**가 요소의 정체성을 가르는
핵심이고, 여기에 소요시간, 공구 사용 여부, 보조손 개입 여부를 더한다. 위치는
화면 크기로 정규화한다.

주기 탐지는 "p칸 떨어진 요소끼리 얼마나 닮았나"를 p마다 계산해서 가장 짧은 주기를
고른다. 두 가지가 중요하다.

- **평균이 아니라 중앙값.** 한 사이클에서 순서가 뒤바뀌어도 주기 판정이 흔들리면
  안 된다. 평균을 쓰면 어긋난 사이클 하나가 전체를 망친다.
- **참주기의 배수를 걸러낸다.** 주기가 2면 4도 8도 비용이 똑같이 낮다. 최소 비용에서
  데이터 산포의 25% 안에 드는 가장 짧은 주기를 택한다.

주기를 알면 `--period`로 직접 줘도 된다. 사이클 경계(오프셋)는 위치별 분산이
가장 작아지는 지점으로 자동 선택한다.

사이클을 나눈 뒤에는 DTW로 서로 정렬한다. 요소 개수가 사이클마다 다를 수 있기
때문이다. 참조 사이클은 다른 사이클들과 가장 닮은 것으로 고른다. 정렬 결과에서
한 사이클에 **누락과 추가가 짝으로 나오고 두 요소가 닮았으면 순서가 바뀐 것**으로
판정한다. 이게 포카요케에서 제일 중요한 신호다.

### 출력

- `*_elements.csv` — 요소 전체 목록. 사이클·순번·시간·서블릭 구성·집는 위치·놓는 위치
- `*_standard.csv` — 표준 요소표. 중앙값, IQR, 최소/최대, 출현 횟수, 정미시간, 표준시간
- `*_standard.json` — 위 내용 전체와 변동 구간 목록
- `*_cycles.svg` — 사이클 정합 차트. 맨 위가 표준, 아래가 각 사이클. 순서가 어긋난
  요소는 점선 테두리와 `*` 표시

### 표준시간에 대해

관측시간은 표준시간이 아니다. 시스템은 요소별 **중앙값**을 낸다. 평균이 아니라
중앙값인 이유는 부품을 한 번 떨어뜨린 사이클이 평균을 다 망치기 때문이다.

표준시간 = 중앙값 × 레이팅 × (1 + 여유율)

레이팅(수행도 평가)은 작업자의 숙련도를 사람이 판단하는 값이라 자동화할 수 없다.
`--rating`, `--allowance`로 입력하고, 기본값은 각각 1.0과 0.15다. 출력물에도
"사람이 정한 값"으로 명시된다.

### 검증 상태

합성 특징 데이터 120건(주기 1~5, 노이즈 2~10%)에서 주기 탐지 120/120 정확.
실제 손 이미지로 만든 6사이클 2요소 영상에서 요소 12개를 정확히 분할하고,
주기 2·사이클 6회를 신뢰도 0.948로 검출했으며, 일부러 순서를 바꿔 넣은
5번째 사이클을 "순서 이탈"로 정확히 집어냈다.

실제 작업 영상에서는 임계값 조정이 필요하다. 특히 요소 분할은 `RL` 검출에
전적으로 의존하므로, `therblig_tag.py`로 쥐기/놓기가 제대로 잡히는지 먼저
확인하고 `--close-curl`을 맞춘 다음 이 단계로 넘어가야 한다.

### 다음 단계

M2에서 작업영역(존)을 정의해 요소에 이름을 붙이고, M3에서 요소별 대표 사진을
자동 캡처한다. 현재 요소 이름은 `null`이고 동작 구성(`D>TE>G>TL>RL`)만 나온다.

## M2 — 작업영역 정의와 요소 명명

M1이 낸 요소는 `D>TE>G>TL>RL` 같은 동작 구성뿐이라 작업표준서에 쓸 수 없다.
"부품박스 A에서 브래킷 집어 지그에 조립"이 되려면 화면의 어디가 무엇인지 한 번
알려줘야 한다. 그게 존(zone) 정의다.

### 순서

```bash
# 1. 존 정의용 배경 프레임 (브라우저가 못 읽는 코덱일 때만 필요)
python motion/grab_frame.py work.mp4 --at 5 --out frame.png

# 2. zone_tool.html 을 브라우저에서 연다 (로컬 파일로 열면 된다)
#    영상 또는 frame.png 를 불러오고, M1이 만든 *_elements.csv 도 같이 얹는다
#    사각형을 그리고 이름·종류·품명을 넣은 뒤 zones.json 저장

# 3. 존을 붙여 다시 돌린다
python motion/build_standard.py work.mp4 --zones zones.json --out-dir out
```

### 존 정의 도구

`zone_tool.html` 은 의존성 없는 단일 HTML 파일이다. 브라우저에서 그냥 열면 된다.

핵심은 **요소 위치 겹쳐보기**다. M1이 만든 `*_elements.csv` 를 얹으면 손이 실제로
집은 지점(붉은 점)과 놓은 지점(주황 점)이 프레임 위에 찍힌다. 그 뭉치를 감싸게
사각형을 그리면 된다. 어디에 존이 필요한지 추측할 필요가 없다.

존 종류는 여섯 가지고, 이게 이름 템플릿을 고른다.

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| `part` | 부품을 집어오는 곳 | 부품박스, 대차, 슈트 |
| `jig` | 조립·가공하는 곳 | 지그, 치구, 작업대 |
| `tool` | 공구를 집는 곳 | 공구걸이, 드라이버 거치대 |
| `output` | 완성품을 놓는 곳 | 배출 슈트, 완성품 박스 |
| `inspect` | 확인하는 곳 | 검사대, 게이지 |
| `other` | 그 외 | |

품명(`item`)은 선택이지만 넣으면 이름이 훨씬 낫다. 부품박스 A에 "브래킷"을 넣으면
"브래킷을 조립 지그에 조립"이 나오고, 안 넣으면 "부품박스 A 부품을 조립 지그에 조립"이 된다.

### 이름을 만드는 규칙

집는 위치와 놓는 위치가 각각 어느 존에 들어가는지 보고, 두 존의 종류 조합으로
문장을 고른다.

| 집는 곳 → 놓는 곳 | 생성되는 이름 |
| --- | --- |
| part → jig | `{품명}을 {지그명}에 조립` |
| part → output | `{품명}을 {배출명}에 적재` |
| jig → output | `완성품을 {배출명}에 배출` |
| 무엇이든 → inspect | `{품명}을 {검사명}에서 검사` |
| tool에서 집고 `U`(사용) 포함 | `{공구명}으로 {대상}에 작업` |
| 같은 존 안에서 | `{존명}에서 작업` |

보조손이 `H`(잡고있기)면 `(좌수 지지)` 가 뒤에 붙는다. 조사(을/를, 으로/로)는
받침을 보고 자동으로 고른다.

점이 어느 사각형에도 안 들어가면 `--zone-tol`(기본 0.05, 화면 비율) 안의 가장
가까운 존으로 본다. 그것도 없으면 이름을 반만 만들고 경고한다.

### 명명률을 보라

출력의 `명명률`은 집는 곳과 놓는 곳이 **둘 다** 존에 들어간 요소의 비율이다.
한쪽만 들어가면 `부분명명`으로 따로 센다. 0.8 아래면 존이 덜 정의된 것이고,
경고에 몇 개가 부분인지 미명명인지 나온다. 한 번도 안 쓰인 존이 있으면 그것도
알려준다. 잘못 그렸거나 그 작업에 없는 영역이라는 뜻이다.

### 지금 나오는 것과 아직 안 나오는 것

이름은 **초안**이다. "브래킷을 조립 지그에 조립"까지는 데이터로 뒷받침되지만,
그게 압입인지 삽입인지 가체결인지는 영상에 없다. 검수 단계에서 사람이 고친다.
급소와 급소의 이유는 M4와 M5에서 다룬다.

### 검증 상태

6사이클 2요소 영상에 존 4개(부품박스 A/B, 조립 지그, 완성품 슈트)를 정의해
명명률 1.0, 요소 이름 "브래킷을 조립 지그에 조립" / "커넥터를 조립 지그에 조립"이
나왔고, 한 번도 안 쓰인 완성품 슈트를 경고로 잡았다. 부품박스 B를 일부러 빼면
명명률이 0.5로 떨어지고 부분명명 6건이 보고된다.

도구는 브라우저에서 실제로 구동해 확인했다. 코덱이 안 맞는 영상에서 안내 메시지,
이미지 로드, CSV 점 오버레이(집은 지점 12·놓은 지점 12), 사각형 3개 그리기,
zones.json 내보내기(정규화 좌표 확인), 다시 불러오기까지 JS 오류 없이 동작한다.

## M3 — 요소별 대표 사진 자동 캡처

작업표준서는 글보다 사진이다. 요소마다 한 장씩 뽑되, 아무 프레임이나 쓰면 손이
흐릿하거나 손에 가려 아무것도 안 보인다.

```bash
python motion/capture_shots.py work.mp4 \
    --standard out/work_standard.json --zones zones.json --out-dir out
```

M1·M2가 만든 `*_standard.json`을 읽으므로, 사진 설정만 바꿔 다시 돌릴 때 손 검출을
처음부터 다시 하지 않는다.

### 언제를 찍을 것인가

M1이 요소를 자를 때 **결정적 순간**을 같이 기록해 둔다. 이 시점 앞뒤 0.4초
(`--window`)에서 프레임을 훑는다.

| 순간 | 왜 좋은 사진인가 | 가중치 |
| --- | --- | --- |
| 쥐기 완료 | 무엇을 어떻게 쥐었는지 보인다 | 1.00 |
| 위치 확정 | 어디에 어떤 자세로 놓이는지 보인다 | 0.95 |
| 사용 중 | 공구 작업 장면 | 0.90 |
| 놓기 직전 | 조립된 상태가 보인다 | 0.85 |
| 요소 중간 | 위 넷이 없을 때의 대비책 | 0.50 |

### 어느 프레임을 고를 것인가

점수 = `0.6 × 선명도 + 0.2 × 손 검출 신뢰도 + 0.2 × 순간 가중치`

선명도는 라플라시안 분산인데 **손 주변 박스에서만** 계산한다. 화면 전체로 재면
배경이 선명하고 손만 흔들린 프레임이 높은 점수를 받는다. 작업표준서에서 봐야
하는 건 손이다.

요소당 3장을 뽑되 두 가지 제약을 건다. 서로 0.25초 이상 떨어져 있어야 하고,
가능하면 **서로 다른 순간**에서 고른다. 같은 순간에서 거의 같은 사진 세 장을
주는 것보다, 쥐기·놓기·작업 중 한 장씩이 검수할 때 쓸모 있다.

대표 사진을 뽑을 사이클은 **소요시간이 중앙값에 가장 가까운 사이클**이다.
제일 빠른 사이클을 쓰면 표준서 사진이 실제 작업과 달라진다.

### 주석

- 집는 곳 존은 붉은색, 놓는 곳 존은 청록색 사각형과 라벨
- 손 골격 21점
- 하단 캡션 바: 요소 번호와 이름, 순간 종류, 시각, 요소 소요시간

한글은 OpenCV로 못 찍어서 캡션만 PIL로 얹는다. 폰트는 나눔고딕, Noto CJK,
애플 SD 고딕, 맑은 고딕 순으로 자동 탐색하고 `--font`로 지정할 수 있다.
못 찾으면 경고하고 캡션이 네모로 나온다.

### 출력

- `shots/{stem}_e01_1_grasp_end.jpg` — 원본 프레임
- `shots/{stem}_e01_1_grasp_end_annot.jpg` — 주석본
- `*_shots.png` — 요소별 1순위 사진을 모은 대표 사진 시트. 검수할 땐 이것만 본다
- `*_shots.json` — 요소별 후보 3장의 시각·점수·파일명

### 검증 상태

6사이클 영상에서 요소 2개 × 후보 3장을 뽑았고, 세 장이 서로 다른 순간
(쥐기 완료 / 놓기 직전 / 요소 중간)에서 선택됐다. 주석본에 존 사각형과 라벨,
손 골격, 한글 캡션이 모두 정상 렌더링된다.

프레임 읽기는 무작위 탐색 대신 순차 스캔으로 필요한 것만 가져오는데, 연속 프레임과
범위 밖 요청을 섞어 직접 탐색 결과와 대조해 일치를 확인했다.

### 남은 것

사진이 **정말 쓸 만한지**는 사람이 봐야 안다. 목표는 1순위 사진 채택률 70%였고,
이건 실제 작업 영상으로만 잴 수 있다. 지금 합성 영상은 배경이 단색이라 선명도
점수가 거의 변별되지 않는다. 실제 영상에서는 이 부분이 제일 크게 작동할 것이다.

## M4 — TWI 작업지도서 생성

M1~M3이 낸 순서·시간·이름·사진을 TWI 작업지도(Job Instruction) 3열 양식의
워드 문서로 묶는다.

```bash
cd motion && npm install docx        # 최초 1회
python motion/build_ji.py \
    --standard out/work_standard.json --shots out/work_shots.json --out-dir out \
    --job-name "브래킷 조립" --process "1공정 조립" --author "홍길동" --doc-no "WI-ASM-001"
```

문서 생성은 `docx`(npm) 로 하고, 내용 구성은 파이썬이 한다. `ji_spec.py` 가
`*_ji_spec.json` 을 만들고 `ji_sheet.js` 가 그걸 찍는다. 양식을 바꿀 일이 생기면
렌더러만 갈아끼우면 된다.

### 왜 TWI 3열인가

"동작을 순서로 나누고 작업 방법을 구성한다"는 요구에 정확히 맞는 검증된 틀이다.

- **주요단계** — 작업을 진행시키는 단위. M1·M2의 작업요소가 그대로 들어간다
- **급소** — 성공을 좌우하는 것, 안전, 작업을 쉽게 하는 요령
- **급소의 이유** — 왜 그래야 하는지

여기에 사진 열과 순번 열을 더해 A4 가로로 앉힌다.

### 급소는 근거가 있는 것만 만든다

관측 데이터에 신호가 있을 때만 급소 초안을 낸다. 없는 급소를 지어내면 그럴듯한
거짓말이 든 표준서가 된다.

| 관측 신호 | 생성되는 급소 초안 |
| --- | --- |
| 순서 이탈 | 이 순서를 지킬 것. 순서가 바뀐 사이클 번호까지 명시 |
| 누락 | 빠뜨리기 쉬움. 관측 N/M 회만 수행됨 |
| 시간 산포 | 작업시간 편차 큼(범위 표시). 방법이 안정돼 있지 않다 |
| 동작구성 불일치 | 사이클마다 손동작 구성이 달랐다. 방법을 통일할 것 |
| 장거리 이동 | 손 이동 거리가 길다. 부품 배치를 재검토할 것 |
| 보조손 사용 | 좌수로 부품을 지지 |
| `U`(사용) 포함 | 공구 사용 구간. 체결 상태를 확인할 것 |

신호가 하나도 없는 단계는 "(관측에서 나온 신호 없음 — 기입 필요)"로 비워 둔다.

**급소의 이유 열은 전부 빈칸이다.** 영상에 그 정보가 없기 때문이다. 점선을 그어
두고 작성자가 채우게 한다. 이걸 자동으로 채우면 안 된다.

### 문서 구성

1쪽에 표제, 관리정보(문서번호·개정·작성일·작성자·승인), 작업조건(설비·치공구·보호구는
빈칸), 관측 요약, 그리고 작업분해표가 들어간다. 상단에 "이 문서는 초안이며 승인 전에는
현장에 게시하지 말 것"이라는 경고를 박아 둔다.

부록 A는 사이클별 소요시간과 중앙값 대비 편차, 그리고 변동 구간 목록.
부록 B는 사이클 정합 차트다. SVG 변환기를 요구하지 않도록 PIL로 직접 그린다.

마지막 장은 **승인 전 채워야 할 항목 체크리스트**다. 급소의 이유 미기입, 사진 없는
단계, 신호가 없어 비워 둔 급소, 사이클 부족, 레이팅 미평가가 여기 모인다. 레이팅이
기본값 1.0이면 "수행도 평가를 하지 않은 값"이라고 명시한다.

빈칸은 연한 베이지 음영으로 칠해서 문서만 봐도 어디를 채워야 하는지 보인다.

### 글꼴

문서 글꼴은 `--font-name`(기본 맑은 고딕)으로 지정한다. 워드가 열리는 PC에
그 글꼴이 있어야 한다. 부록 차트의 한글은 이미지로 구워지므로 실행 환경에
한글 TTF가 필요하고, 없으면 `--font` 로 경로를 준다.

### 검증 상태

생성된 문서를 OOXML 스키마로 검증해 통과했고(문단 117개), PDF로 변환해 4쪽 전체를
눈으로 확인했다. 표 너비 합계, 사진 삽입, 한글 렌더링, 빈칸 음영, 부록 차트,
체크리스트가 모두 정상이다.

처음엔 부록 차트 제목이 워드 제목과 이미지 안에 겹쳐 두 번 나왔고, 변동 구간
종류가 `reorder` 같은 영문 그대로 나왔다. 둘 다 고쳤다.

## M6 — 검수 화면

여기서 30분 검수가 성립한다. `review_tool.html` 을 브라우저에서 열고 결과 폴더와
영상을 넣으면 요소 목록·사진 후보·급소 초안·영상 구간이 한 화면에 뜬다.

```bash
# 1. review_tool.html 을 브라우저에서 연다 (로컬 파일)
#    결과 폴더(build_standard.py + capture_shots.py 출력)와 원본 영상을 고른다
#    이름·급소·급소의 이유를 고치고 사진을 고른 뒤 review.json 저장

# 2. 검수 결과를 반영해 문서를 다시 찍는다
python motion/build_ji.py --standard out/work_standard.json \
    --shots out/work_shots.json --review review.json --out-dir out
```

### 검수 속도를 만드는 것

**영상 구간 반복 재생**이 핵심이다. 요소를 고르면 그 요소의 대표 사이클 구간만
루프로 돈다. 2초짜리 구간을 서너 번 보면 이게 무슨 작업인지 바로 안다. 사진만
보고 판단하려 들면 검수가 안 끝난다.

**관측 신호를 먼저 보여준다.** 요소마다 상단에 순서 이탈·산포·누락 같은 플래그와
동작 구성, 관측 횟수가 뜬다. 급소 초안이 왜 그렇게 나왔는지, 무엇을 눈여겨봐야
하는지가 먼저 보인다.

**키보드로 넘긴다.** <kbd>J</kbd>/<kbd>K</kbd> 이전·다음, <kbd>Enter</kbd> 확인하고
다음, <kbd>1</kbd><kbd>2</kbd><kbd>3</kbd> 사진 선택, <kbd>Space</kbd> 재생·정지.
마우스로 왔다 갔다 하면 요소당 1분이 2분이 된다.

**자동 저장.** 브라우저 localStorage 에 계속 저장하므로 실수로 새로고침해도
이어서 한다. 다시 열면 "이전 검수 내용을 복구했다"가 뜬다.

### 검수 상태

요소마다 미검토 / 수정됨 / 확인됨 세 상태가 있고 상단 막대에 진행률이 뜬다.
`확인하고 다음` 을 눌러야 확인됨으로 바뀐다. 손도 안 댄 요소가 문서에 그대로
실리는 걸 막기 위해서다. 검수를 안 거친 요소는 문서의 체크리스트에 "검수 화면에서
아직 확인하지 않았다"로 올라간다.

### 문서로 돌아가는 경로

`review.json` 에는 요소별 이름·급소·급소의 이유·선택한 사진·상태와 문서 헤더
정보(작업명·공정·문서번호·작성자·설비·치공구·보호구)가 들어간다. `build_ji.py --review`
로 넘기면 전부 문서에 반영된다. CLI 인자를 같이 주면 CLI 가 이긴다.

급소의 이유가 채워진 칸은 베이지 음영이 사라지고 본문으로 들어간다. 체크리스트도
줄어든다. 검수 전 4건이던 미기입 항목이 검수 후 1건(레이팅 미평가)만 남는다.

### 검증 상태

브라우저에서 실제로 구동해 전 과정을 확인했다. 결과 폴더 로드(요소 2개, 플래그
`순서 이탈`, 급소 초안 1건, 사진 후보 3장, 썸네일 3장 모두 로드), 이름 수정,
급소 직접 추가, 급소의 이유 기입, 대안 사진 선택, 확인 처리로 진행률 0/2 → 2/2,
review.json 내보내기까지 JS 오류 없이 동작한다. 폴더 선택이 안 되는 환경을 위해
파일 직접 선택 경로도 따로 두고 같이 확인했다.

내보낸 review.json 을 `build_ji.py --review` 에 넣어 문서를 다시 찍었을 때,
수정한 이름("브래킷을 지그에 삽입"), 검수에서 추가한 급소, 기입한 급소의 이유,
검수에서 고른 대안 사진(놓기 직전 컷)이 모두 문서에 반영됐다.

이 과정에서 두 가지를 고쳤다. 사진 경로를 `--out-dir` 기준으로 찾고 있어서
출력 폴더를 따로 주면 사진이 다 빠졌다. 지금은 `shots.json` 위치를 기준으로
찾고 `--shot-dir` 로 덮어쓸 수 있다. 그리고 급소의 이유 칸이 기입 여부와 무관하게
항상 빈 점선으로 그려지고 있었다.

### 남은 것

M5(포카요케 리스크 엔진)만 남았다. 기획대로 불량 이력이나 공정 FMEA 가 붙어야
값이 나온다. 데이터 없이 만들면 그럴듯한 목록만 나온다.

그리고 전체 검증이 아직 합성 영상 기준이다. 목표였던 "10분 영상 → 30분 검수"는
실제 작업 영상으로만 잴 수 있다.

## M5 — 포카요케 리스크 신호

```bash
python motion/find_risks.py --standard out/work_standard.json \
    --zones zones.json --defects defects.csv --out-dir out

# 문서 부록으로 붙이려면
python motion/build_ji.py --standard out/work_standard.json --shots out/work_shots.json \
    --review review.json --risks out/work_risks.json --out-dir out
```

### 이 단계가 낼 수 있는 것과 없는 것

포카요케는 "이 불량이 난다"는 사실에서 출발한다. 영상에는 불량 정보가 없다.
그래서 여기서 나오는 건 **리스크 신호**와 일반적인 **대책 후보**까지고,
채택과 투자 판단은 사람이 한다.

### 검출하는 신호 여덟 가지

| 신호 | 근거 | 기본 심각도 |
| --- | --- | --- |
| 작업 순서가 사이클마다 다름 | 사이클 정합의 순서 이탈 | 중 |
| 작업시간 산포가 큼 | IQR ÷ 중앙값 > 0.3 (0.5 초과면 상) | 중·상 |
| 체결·가공 직후 확인 동작 없음 | `U` 뒤에 정지·검사 동작이 0.4초 미만 | 상 |
| 잡고만 있는 시간이 김 | 요소 시간의 20% 초과가 `H` | 중 |
| 표준에 없는 동작이 추가됨 | 정합에서 대응되지 않는 요소 | 상 |
| 부품 공급 위치가 서로 인접 | `part` 존 사이 간격 0.06 미만 | 중 |
| 손 이동 거리가 김 | 집는 지점과 놓는 지점 거리 | 하 |
| 한 손만 일함 / 양손 유휴 | 양손 서블릭 동시 분석 | 하 |

각 신호에는 관측 수치(`근거`), 어디서 나온 판단인지(`판단 근거`), 의심되는 불량,
그리고 포카요케 후보가 **예방(원인 차단)** 과 **검출(발견)** 로 나뉘어 붙는다.

### 불량 이력을 붙이면

`--defects` 에 CSV(열: `불량모드`, `건수`, `키워드`)를 주면 키워드를 **요소 이름과
신호 이름**에 맞춰 연결하고, 연결된 신호는 심각도를 한 단계 올린다. 단순 문자열
포함 매칭이라 사람이 한 번 확인해야 하고, 키워드를 좁게 쓸수록 정확하다.

처음에는 "의심 불량" 목록에도 키워드를 맞췄는데, 그건 이쪽에서 써 넣은 예시
문구라 아무 신호에나 다 붙었다. 관측에서 나온 것에만 맞추도록 좁혔다.

불량 이력을 주지 않으면 CLI 와 문서 부록 양쪽에 "지금 심각도는 관측 신호만 보고
매긴 값"이라고 명시하고, 승인 전 체크리스트에도 올린다.

### 출력

- `*_risks.json` — 신호 전체와 요약
- `*_risks.csv` — 엑셀에서 바로 검토·배포할 수 있는 표 (BOM 포함)
- 작업지도서 **부록 C** — 심각도 색상, 근거, 연결된 불량 이력, 대책 후보

### 검증 상태

여덟 규칙이 모두 걸리도록 만든 시험 데이터에서 8/8 검출, 예상 밖 검출 0건.
불량 이력 연결도 확인했다 — `체결 누락/키워드 체결` 은 "스크루 2본 체결" 요소의
신호 세 건에만, `오조립/키워드 순서` 는 순서 이탈 신호에만 붙었다.

합성 작업 영상에서는 일부러 순서를 바꿔 넣은 사이클을 `작업 순서가 사이클마다
다름`(상, 오조립 7건 연결)으로, 한 손만 나오는 영상 특성을 `한 손만 일하고 있음`(하)
으로 잡았다.

존 간격을 처음에 중심점 기준으로 재서 인접 부품박스를 놓쳤다. 사각형 사이의 실제
간격으로 고쳤다(0.08 → 0.010).
